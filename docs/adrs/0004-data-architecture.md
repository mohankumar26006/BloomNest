# ADR 0004: Data Architecture

## Context
BloomNest relies on a combination of dynamic user-generated data (e.g., daily vitals, journal entries) and static, medically-aligned referential data (e.g., week-by-week fetal development metrics, standard Indian prenatal scan schedules, Garbha Sanskar stotras, baby names). The architecture must clearly delineate between these two data types.

## Decision
We implemented a **Bifurcated Data Architecture**: separating Static Reference Data from Dynamic User State.

### 1. Static Reference Data (`src/data/`)
All immutable, referential data is stored in static TypeScript files inside the `data` directory:
- `pregnancyWeeksData.ts`: Holds detailed JSON-like objects for all 40 weeks of gestation (fruit sizes, ultrasound metrics, milestones).
- `medicalScans.ts`: Contains the standard Indian ultrasound schedule.
- `babyNames.ts`: A curated database of baby names with meanings, origins, and numerology.
- `nutritionRecipes.ts`: Trimester-specific meal plans and recipes.
- `translations.ts`: The localization dictionary.

**Why?** Storing this data in code (rather than a database) ensures instant access, zero network requests, and absolute reliability. It acts as the "source of truth" for clinical guidelines and informational content.

### 2. Dynamic User State (`AppContext.tsx`)
All mutable data generated by the user is managed by the `AppProvider`:
- User Profile (name, current week, blood group, EDD).
- Interaction Logs (vitals, kicks, contractions, mood, medicines).
- Checklists (hospital bag, vaccination records, birth plan).

**Why?** This data must be persisted across sessions. By isolating it from the static data, the `localStorage` payload remains incredibly lean—only storing what the user actually modifies or records, rather than saving redundant static content.

## Consequences
### Positive
- **Performance:** Rendering the 40-week baby development visualizer is instantaneous because the data is bundled with the JavaScript, requiring no API fetch.
- **State Efficiency:** The local storage sync mechanism is incredibly fast because it only serializes the lean, dynamic arrays, not the massive static databases.

### Negative / Risks
- **Update Cycle:** Updating clinical guidelines, adding new baby names, or fixing a typo in a nutrition recipe requires a full code deployment and application build, rather than a simple database CMS update.
- **Bundle Size:** Large static datasets (like thousands of baby names) will inflate the initial JavaScript bundle size, impacting Time to Interactive (TTI) on slow connections.

## Future Considerations
To address bundle size inflation, we should implement **Lazy Loading / Code Splitting** for massive static datasets. For example, `babyNames.ts` could be converted to a static JSON file stored in the `public` directory and fetched dynamically only when the user visits the Baby Names page. This would drastically reduce the main bundle size while maintaining the benefits of a static architecture.
